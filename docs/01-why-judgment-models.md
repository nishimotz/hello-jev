# 01. なぜ判断専用モデルか

## 汎用 LLM に判断を頼むと何が起きるか

汎用 LLM に「このメールは緊急か」と聞くと、文章で返ってくる。
JSON 形式を指示すれば、だいたいは従う。だが次の問題が残る。

- **遅い**。トークンを1つずつ生成するので、判断1つに秒単位かかる
- **高い**。出力トークンは入力の数倍の課金になる
- **確信度が信用できない**。`"urgent"` と返っても、どれくらい確信しているか
  分からない。確率を出させても**校正されている保証が無い**
- **judgment が独立しない可能性がある**。複数の問いを一度に投げたとき、
  他の問いが隠れた文脈として判断に影響しうる

**形式が崩れるかどうかは本質ではない。** JSON schema を制約デコーディングで
渡せば形式は守られる（`docs/06` に実測）。壊れるのは**確信度**のほうで、
そこが高信頼システムを作る上で致命的になる。

この 2 点は、**構造化出力を持つモデルでも埋まらない。** Apple の
オンデバイスモデルは `@fm.generable` で型を縛れるが、返る `float` は
同じ入力で 0.00 から 1.00 まで動き（`docs/07`）、判断も順序と会話履歴で
変わった（`task9`）。**形を縛ることと、確信度を保証することは別**である。

なお「遅い・高い」は Apple のオンデバイスモデルには当たらない。
ローカルで無料、1 回 0.5 秒である。残る差は確信度と独立性のほうになる。

## 判断専用モデルという発想

Jev は判断だけを行う。出力は次の3型に限られる。

- `noul` — yes である確率
- `choice` — 定義済み選択肢から1つ。各選択肢の確率と confidence
- `score` — 順序付きレベル上のスコア。各レベルの確率と confidence

定義した形式の値しか返さないので、**形式エラーは仕組みの上で起きない**。
そして確率が返るので、**確信度で処理を分けられる**。

## 設計思想: 制御フローはコードが持つ

判断専用モデルは、次の一手を決めない。決めるのはコード。

```
モデルの仕事: 状態を受け取り、型付きの判断を確信度付きで返す
コードの仕事: 判断と確信度を読み、次に何をするか決める
```

この分離が、高信頼システムの土台になる。
プロンプトに挙動を書くのではなく、判断の型と閾値をコードで定義する。
