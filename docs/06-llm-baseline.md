# 06. 汎用 LLM と比べる

`docs/05` の比較は、実測しないと何も言えない。
ここでは ollama 上の汎用 LLM に同じ判断をやらせ、Jev と何が違うかを見る。

**重要な前提: 以下はすべて1つの環境での観測であり、一般則ではない。**
モデル、量子化、ollama のバージョン、実行場所（ローカルかクラウドか）で
挙動は変わりうる。自分の環境で確かめること。

## 実行

```bash
# task5: LLM に確率を出させる
python3 examples/task5_llm_baseline.py

# task6: criteria の書き方だけを変えて比べる
python3 examples/task6_criteria_matters.py
```

環境変数:

| 変数 | 既定 | 意味 |
|---|---|---|
| `OLLAMA_MODEL` | `gemma4:12b` | 使うモデル |
| `OLLAMA_HOST` | `http://localhost:11434` | ollama の場所 |
| `OLLAMA_THINK` | `0` | `1` で思考を有効にする |

## 実測した環境

| 項目 | 値 |
|---|---|
| モデル | `gemma4:12b`（Q4、7.6 GB） |
| 実行 | ローカル、Apple Silicon 32 GB、100% GPU |
| ollama | 0.34.1 |
| temperature | 0 |
| 形式 | `format` に JSON schema を渡す |

## 分かったこと

### 1. 形式は守られる（この環境では）

JSON schema を `format` に渡すと、**40回中40回**で完全な JSON が返った。
`{"noul": 1.0}` のような形で、キーが欠けたり説明文が混ざることはなかった。

ollama は**制約デコーディング**でトークンの選択肢を schema に合うものだけに
制限する。仕組み上、形式は壊れにくい。ただしこれは**実装依存**であり、
モデルやサーバーが変われば保証はない。

`format: "json"`（schema ではなく JSON モード）にすると、形式は緩くなる。
同じ問いで `{"noul": 0.1}` ではなく **`{"probability": 0.1}`** が返った。
キー名が指示に従わない。

**「形式が崩れる」は、制約デコーディングを使えば起きにくい。**
ここは `docs/01` の主張を訂正する必要がある。

### 2. 同じ入力なら同じ値（この環境では）

temperature=0 で、`請求書の金額が間違っています。確認をお願いします。` を
5回投げると、**5回とも 0.8** だった。temperature=1 でもほぼ同じ値。

**再現しないのではなく、値が信用できない**というのが実態に近い。

### 3. 値は criteria の書き方に依存する

同じ state で、prompt の criteria だけを変えた（`task6`）。

| state | なし | 片側だけ | 両側を書く |
|---|---|---|---|
| 明確に緊急 | 1.00 | 1.00 | 1.00 |
| **要確認の依頼** | **0.40** | **0.30** | **0.30** |
| 明確に非緊急 | 0.10 | 0.00 | 0.00 |

`要確認の依頼` は「請求書の金額が間違っています。確認をお願いします。」
—— 明らかに急ぎではないが、**依頼**ではある。

criteria に「`check` や `confirm` を求めるだけでは緊急ではない」と書くと
**0.40 → 0.30** に下がった。書き方次第で値が動く。

これは `docs/02` の「**criteria は両側を書く**」が LLM でも効くことの
実証である。同時に、**基準を書かなければ値が定まらない**ことも意味する。

### 4. 思考モデルは判断には過剰

`gemma4:12b` は思考モデルで、既定では長い `thinking` を返す。

| `think` | eval_count | 所要時間 |
|---|---|---|
| 既定（思考あり） | 222 | 12〜26 秒 |
| `think=false` | 10〜12 | 1 秒 |

**形式はどちらも同じく守られた。** 判断だけを取るなら思考は不要で、
切れば10倍以上速い。

なお思考ありで、ごく稀に `content` が空になることがあった。
思考だけで生成が終わる場合がある。`task5` はこれを検出してエラーにする。

## Jev と何が違うのか

| | ollama + gemma4:12b | Jev |
|---|---|---|
| 形式 | schema で縛れる（実装依存） | 型として定義済み |
| 確率 | 出るが**校正は未検証** | 較正済みとされている |
| 判断の独立性 | **未検証** | 質問ごとに独立 |
| criteria の役割 | 効くが「お願い」 | 判断の定義 |
| 速度 | 1 回 1 秒（ローカル） | 100 ms 程度 |
| コスト | 0（ローカル） | 入力トークン従量 |

**この表のうち、確かめたのは形式・criteria・速度だけ。**
「校正」と「独立性」は Jev 側で測っていないので、優劣は言えない。

## 次に測るべきこと

1. **較正** — 正解ラベル付きのサンプルで、確率の帯ごとの正答率を見る。
   `docs/05` の手順そのもの。
2. **判断の独立性** — 単独で聞いた値と、複数同時に聞いた値を比べる。
   Jev は並列でも独立とされている。LLM は未検証。
3. **モデルによる差** — 小さいモデルほど崩れるのか。量子化の影響は。
4. **Jev 側の実測** — 同じサンプルで Jev を回さないと比較にならない。

## 注意

- ここに書いた数値は**1環境の観測**であり、一般則ではない
- LLM が出す確率を、Jev の確率と同じ意味で閾値に使ってはいけない
- 較正を確かめずに自動化の閾値を決めると、`docs/03` のアンチパターンに落ちる

## クラウドを使わない比較

`docs/07` は同じことを Apple のオンデバイスモデルで確かめている。
**ネットワークも課金も要らない**ので、こちらより手軽に試せる。
ただし結論は同じで、返る数値は確率として較正されていない。
