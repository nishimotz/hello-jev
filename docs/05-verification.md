# 05. 仮説の検証

## 何を確かめるのか

「かしこい選択だけを行う AI を組み合わせて、高信頼システムを作れる」という仮説。
これを測るには、比較対象が要る。

## 比較の設計

同じ判断を、2つの方法で行い、並べる。

| | 汎用 LLM + JSON 指示 | 判断専用モデル |
|---|---|---|
| 出力 | 型付きの確率（schema で縛れる） | 型付きの確率 |
| 確信度 | 出るが**校正は保証されない** | 較正済みとされている |
| 速度 | 1回 秒単位 | 100 ms 程度 |
| コスト | 入出力トークン | 入力のみ |
| 形式エラー | schema 制約で防げる（実装依存） | 仕組み上起きない |
| criteria の役割 | 効くが「お願い」 | 判断の定義 |

**形式エラーは差にならない。** JSON schema を制約デコーディングで渡せば、
形式は守られる（`docs/06` で実測）。差が出るのは**確信度**と**判断の独立性**。

## 測る指標

1. **一致率** — 正解ラベルに対して、どれだけ一致したか
2. **確信度の較正** — 確率の帯ごとに、実際の正答率が対応しているか
   - 0.9 以上の判断は、本当に 9 割以上正しいか
   - ここが崩れていると、閾値による分岐が機能しない
3. **食い違いの中身** — どちらが正しく、どちらが間違ったか。間違いの性質
4. **コスト** — 同じ件数を処理するのにいくらかかったか
5. **レイテンシ** — 1件あたり、またはバッチ全体

## 確信度の較正を測る方法

```
帯          | 件数 | 正答数 | 正答率
0.9 - 1.0   |  120 |   112  | 0.93
0.6 - 0.9   |   80 |    58  | 0.73
0.0 - 0.6   |   40 |    18  | 0.45
```

確率が高い帯ほど正答率が高ければ、較正できている。
この関係が崩れていたら、criteria か state を見直す。

**較正が正しいときだけ、閾値による自動化が安全になる。**
「0.9 以上は自動実行」を根拠づけるのは、この表。

## 仮説がどこで崩れうるか

- **判断の境界が曖昧なタスク** — criteria を書いても、人間でも意見が割れる場合。較正が崩れる
- **state に必要な情報を入れ忘れる** — モデルは文脈を持たない。渡さなければ判断できない
- **判定単位が決まっていない** — 「この文書は関連するか」の「文書」が何を指すか曖昧だと、criteria が固定できない
- **確率を無視して値だけ使う** — 汎用 LLM との差が消える。仮説の利点を捨てている

## 検証の手順

1. 正解付きのサンプルを用意する（20〜50件で傾向は見える）
2. 判断専用モデルと汎用 LLM、両方に通す
3. 一致率、較正、コスト、レイテンシを記録する
4. 食い違いを分類する（どちらが正しいか、なぜか）
5. 閾値を較正し、自動化してよい帯を決める

**結果は「実運用で試した」までを報告し、判定基準の具体や閾値の実値は公開しない。**
